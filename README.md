# Events API

REST API для управления мероприятиями.

# Технологии

- .NET 10
- C#
- Entity Framework Core
- PostgreSQL
- OpenAPI
- Swagger UI
- xUnit
- FluentAssertions

## Запуск

Перед запуском необходимо установить:

- .NET 10 SDK;
- PostgreSQL.

Собрать и запустить проект из папки 
Swagger доступен по адресу: `http://localhost:5161/swagger/index.html`

Запуск тестов:
- dotnet test

## Эндпоинты

| Метод  | Путь              | Описание                       | Статусы       |
|--------|-------------------|--------------------------------|---------------|
| GET    | /events           | Получить список всех событий   | 200           |
| GET    | /events/{id}      | Получить событие по ID         | 200, 404      |
| POST   | /events           | Создать событие                | 201, 400      |
| PUT    | /events/{id}      | Обновить событие               | 204, 400, 404 |
| DELETE | /events/{id}      | Удалить событие                | 200, 404      |
| POST   | /events/{id}/book | Создать заявку на бронирование | 202, 404, 409 |     |
| GET    | /bookings/{id}    | Получить статус бронирования   | 200, 404      |

#### Параметры Get /events запроса (Query Parameters)

| Параметр   | Тип        | Обязательный | По умолчанию | Описание                           |
|:-----------|:-----------|:-------------|:-------------|:-----------------------------------|
| `title`    | `string`   | Нет          | —            | Фильтр по наименованию события.    |
| `from`     | `DateTime` | Нет          | —            | Фильтр по дате начала события .    |
| `to`       | `DateTime` | Нет          | —            | Фильтр по дате завершения события. |
| `page`     | `integer`  | Нет          | `1`          | Номер текущей страницы.            |
| `pageSize` | `integer`  | Нет          | `10`         | Количество элементов на странице.  |


## ❌ Обработка ошибок (Error Responses)
В случае неуспешного запроса API возвращает стандартный формат ошибок **Problem Details (RFC 7807)**.

### Коды ответов при ошибках

| Код                  | Причина                               | Пример сценария                                        |
|:---------------------|:--------------------------------------|:-------------------------------------------------------|
| `400 Bad Request`    | Ошибка валидации параметров.          | Не передан обязательный параметр.                      |
| `404 Not Found`      | Ресурс не найден.                     | Запрос несуществующего события.                        |
| `409 Conflict`       | Отсутствие доступных мест на событии. | Попытка забронировать места при отсутствии доступных.  |
| `500 Internal Error` | Внутренняя ошибка сервера.            | Непредвиденный сбой в базе данных или коде.            |


## Модели данных

### Событие

| Поле           | Тип      | Описание                                   |
|----------------|----------|--------------------------------------------|
| Id             | Guid     | Идентификатор                              |
| Title          | string   | Наименование                               |
| Description    | int      | Описание                                   |
| StartAt        | DateTime | Дата начала                                |
| EndAt          | DateTime | Дата окончания                             |
| TotalSeats     | int      | Общее количество мест                      |
| AvailableSeats | int      | Доступное количество мест для бронирования |

### Бронь

| Поле        | Тип           | Описание                                                                                                  |
|-------------|---------------|-----------------------------------------------------------------------------------------------------------|
| Id          | Guid          | Идентификатор брони                                                                                       |
| EventId     | Guid          | Идентификатор события                                                                                     |
| Status      | BookingStatus | Статус бронирования: Pending (создана, ожидает обработки), Confirmed (подтверждена), Rejected (отклонена) |
| CreatedAt   | DateTime      | Дата и время создания брони                                                                               |
| ProcessedAt | DateTime      | Дата и время обработки брони                                                                              |

### Сценарии

Овербукинг:

- Создаёте событие с TotalSeats = 10 через POST /events.
- Успешно бронируете 10 мест через POST /events/{id}/book (например, 10 разных пользователей).
- Пытаетесь забронировать 11-е место.
- Система возвращает ответ 409 Conflict с сообщением о том, что свободных мест нет.

Ожидаемый результат: бронь не создаётся, количество AvailableSeats остаётся равным 0.

Обработка заявок на бронирование выполняется в фоновом сервисе, при бронирование заявки находится в статусе Pending, 
после обработки в фоновом процессе заявка подтверждается или откланяется.

### Интеграционные тесты

Интеграционные тесты проверяют взаимодействие приложения с реальной базой данных PostgreSQL.
Для запуска PostgreSQL в тестах используется **Testcontainers**. Перед запуском интеграционных тестов необходимо, чтобы Docker был установлен и запущен.
Testcontainers автоматически запускает временный контейнер PostgreSQL для тестов и удаляет его после завершения тестов. Благодаря этому интеграционные тесты не используют локальную базу данных разработчика.

## Запуск интеграционных тестов
Схема основной базы данных управляется с помощью Entity Framework Core Migrations.

Создание миграций 
dotnet ef migrations add <MigrationName> --project Infrastructure --startup-project WebAPI

Применение миграций к базе данных
dotnet ef database update --project Infrastructure --startup-project WebAPI

### Хранение данных
Данные приложения хранятся в PostgreSQL.
Если PostgreSQL запущен в Docker-контейнере без подключенного volume, данные могут быть удалены вместе с контейнером.
При использовании постоянного volume данные сохраняются между перезапусками контейнера.
Миграции накатываются автоматически при старте приложения.

###  Архитектура приложения
Архитектура приложения спроектирована на основе принципов чистой архитектуры.
Слови приложения:
- **Domain**, содержит изолированную бизнес-логику, сущности и бизнес-правила;
- **Application** оркеструет бизнес-правила, реализуя пользовательские сценарии;
- **Infrastructure** отвечает за взаимодействие с внешними системами, включая базы данных, кэширование и сторонние сервисы;
- **WebAPO** (или **Presentation**) точка входа в приложение, принимает HTTP-запросы и возвращая ответы пользователю.

Зависимости в проекте направлены строго внутрь, что гарантирует независимость и легкую тестируемость ядра системы.
